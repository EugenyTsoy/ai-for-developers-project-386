# Docker: локальная проверка шага 7

## Вариант запуска

Корневой `Dockerfile` использует три стадии: Node 24 собирает React/Vite;
.NET SDK 10 публикует API и его backend-зависимости; ASP.NET Runtime 10 запускает
API и раздаёт frontend из `wwwroot`. В финальном образе нет Node, SDK и Aspire.
Используются закоммиченные generated-артефакты, без повторной генерации контракта.
Бизнес-логика и API-контракт не изменены. AppHost сохранён для локальной разработки.

Frontend и `/api` доступны на одном origin: CORS, отдельный proxy и
`VITE_API_BASE_URL` не нужны. Прямые запросы `/`, `/booking`, `/events` возвращают
SPA; неизвестные API и отсутствующие assets — 404, а не HTML.

Это минимальная production-упаковка для демонстрации, не надёжное production-хранилище.
Отдельного текста шага 7 из личного кабинета Hexlet в репозитории нет;
реализация опирается на запрос пользователя и текущую спецификацию MVP.
Деплой на хостинг не выполнялся.

## Сборка и проверка

Из корня репозитория, при запущенном Docker с Linux containers:

```sh
docker build -t callbooking:step7 .
docker run --detach --name callbooking-step7 --publish 127.0.0.1:8080:8080 callbooking:step7
node scripts/check-container.mjs http://localhost:8080
```

Для проверки другого порта и IANA timezone:

```sh
docker run --detach --name callbooking-port --env PORT=9090 --env Calendar__Timezone=Europe/Moscow --publish 127.0.0.1:18080:9090 callbooking:step7
node scripts/check-container.mjs http://localhost:18080
```

`PORT` по умолчанию 8080, слушает `0.0.0.0`, приоритетнее URL-настроек ASP.NET.
Невалидное значение вне диапазона 1–65535 останавливает запуск с ошибкой.
Процесс работает без root, как `app` (UID 1654); используйте непривилегированный порт.
`EXPOSE 8080` — метаданные, а не ограничение `PORT` и не публикация на хосте.

В Production контейнер принимает HTTP. TLS должен завершаться на стороне
доверенного reverse proxy/хостинга; сертификатов и HTTPS redirect в контейнере нет.
Forwarded headers не включаются безусловно от любых прокси. Development endpoint
OpenAPI не публикуется. Готовность можно проверять существующим `GET /api/calendar`.

Скрипт требует Node 24, создаёт синтетические данные: запускать **только на
одноразовом локальном экземпляре**. Нужен свободный часовой слот более чем через
час в текущем 14-дневном окне. Проверяются HTML, ссылки на JS/CSS и их загрузка,
404 для неизвестных API/assets, timezone, создание/чтение типов, слоты,
booking/upcoming. Восемь параллельных запросов на один старт у двух типов
(30/45/60 минут) должны дать один 201 и семь 409 с ProblemDetails. Также проверяются
общая сетка стартов через 30 минут, переменный конец и off-grid 400. Повторный запрос
получает 409, upcoming содержит одну новую запись, пересекающиеся слоты исчезают
для всех трёх типов. Это runtime-проверка конечного инварианта; детерминированный
contention проверяется существующими backend-тестами.

## UI с реальным API контейнера

Из `src/frontend/callbooking.web`, PowerShell:

```powershell
$env:VITE_RUNTIME_WEB_URL = 'http://localhost:8080'
npm run test:runtime
Remove-Item Env:VITE_RUNTIME_WEB_URL
```

Opt-in Vitest/RTL/jsdom suite проверяет путь создания типа через UI, выбора
даты в timezone календаря, времени, бронирования, подтверждения, upcoming и исчезновения слота.
Дополнительный сценарий занимает слот другим клиентом между выбором и submit:
UI показывает конфликт 409, обновляет слоты и не показывает ложное подтверждение.
Это не настоящий браузер: RTL рендерит исходный App, не скачанный JS bundle.
Для браузерной проверки открыть сайт контейнера, повторить сценарий и обновить
`/booking`, `/events`.

## Ограничения хранения и безопасности

- `InMemoryCalendarStore` — singleton с коллекциями только в RAM процесса.
  **Любой перезапуск** процесса, падение, redeploy или пересоздание контейнера
  стирает все типы и бронирования. Free-tier sleep с остановкой процесса тоже.
- Docker volume не поможет: записи в файл или БД нет; backup/restore отсутствуют.
- Атомарный check-and-create защищён общим lock только внутри одного процесса.
  Несколько реплик имеют независимые календари и не гарантируют общей защиты
  от конфликтов. Допустим только один экземпляр; rolling deployment тоже может
  временно запустить два экземпляра. Сохранность данных не обещается.
- Коллекции не ограничены по размеру и расходуют память; при потере процесса
  или исчерпании памяти данные теряются.
- По утверждённому MVP авторизации нет. Любой клиент может создать тип и прочитать
  upcoming с именами/email. Для публичной демонстрации допустимы только
  синтетические данные; TLS не решает проблему такого доступа.
- Перед реальной эксплуатацией отдельно согласовать постоянное хранилище,
  межпроцессную атомарность запрета пересечений, миграции, backup/restore и защиту
  персональных данных. В эту задачу они не входят.

Проверка потери данных после создания бронирований:

```sh
docker restart callbooking-step7
```

После готовности `GET /api/event-types` и `GET /api/bookings/upcoming` снова
возвращают `[]`, хотя контейнер тот же: теряется память процесса, не filesystem.
После завершения удалить только созданные для проверки контейнеры:

```sh
docker rm --force callbooking-step7 callbooking-port
```

  финальных исходников успешны. Runtime работает как UID 1654; Node и .NET SDK
  отсутствуют, установлены ASP.NET Core / .NET Runtime 10.0.13.
- `check-container.mjs` прошёл на стандартном 8080 и на `PORT=9090`
  (host 18080, `Europe/Moscow`); проверка финального образа на 8080 повторена.
  В каждом прогоне восемь запросов дали ровно один 201 и семь 409.
- UI runtime suite с API контейнера: **3/3**; повторён на финальном образе.
- В настоящем браузере со скачанным production bundle: создан тип
  `Browser Docker check`, выбран слот, отправлены синтетические имя/email,
  получено подтверждение без PII, запись отображена в upcoming. CSS загружен;
  обновление `/events` и `/booking` сохраняет правильную страницу.
- До `docker restart` API содержал 5 типов и 4 бронирования. После перезапуска
  того же контейнера обе коллекции вернули `200 []`: потеря данных подтверждена.
- Невалидный `PORT=invalid` завершает процесс с ошибкой валидации.
- Backend: **246 passed, 1 skipped** (существующий Windows skip теста IANA-зоны
  без Windows-эквивалента); architecture: **4/4**; frontend: **66/66**.
  Frontend lint, production build и API `dotnet format --verify-no-changes` прошли.
- AppHost Release build прошёл; остаётся предупреждение ASPIRE010 о существующем
  `AspireUseCliBundle=false`. Сам запуск Aspire в этой проверке не выполнялся.
- Хостинг, внешний TLS/proxy, рестарты платформы и несколько реплик не проверялись.
  Docker-проверки пока opt-in, в CI отдельный job не добавлялся.
