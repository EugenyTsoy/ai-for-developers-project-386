# MCP в OpenCode

В корневом `opencode.json` настроен один MCP-сервер: официальный
[Render MCP](https://render.com/docs/mcp-server). Конфигурация использует формат
[OpenCode V2](https://opencode.ai/v2/docs/mcp-servers) (`mcp.servers`).
Для запуска самого CallBooking MCP и ключ Render не нужны.

## Настройка

1. Установите OpenCode V2. Создайте личный API-ключ в
   [Render Account Settings](https://dashboard.render.com/u/settings?add-api-key).
2. Передайте ключ в переменной окружения `RENDER_API_KEY` **серверному процессу** OpenCode.
   Например, в Bash ввод без отображения и сохранения ключа в истории команд:

   ```bash
   read -r -s -p 'Render API key: ' RENDER_API_KEY
   export RENDER_API_KEY
   ```

   В Windows задайте переменную окружения для процесса через свой менеджер
   секретов или настройки пользовательских переменных, затем откройте новый терминал.

   OpenCode V2 по умолчанию использует общий фоновый сервер: он читает конфигурацию
   и подключает MCP. Перезапуск GUI/TUI не перезапускает этот сервер и не обновляет
   его окружение. После установки или смены ключа:

   - Дождитесь завершения активных задач во всех клиентах OpenCode и согласуйте
     перезапуск: общий сервер обслуживает и другие проекты.
   - В том же терминале, где уже задан `RENDER_API_KEY`, выполните:

     ```bash
     opencode service restart
     opencode service status
     ```

     Новый сервер унаследует окружение этого терминала. Затем переподключите клиенты.
     Не перезапускайте сервер из агента посреди выполняющейся задачи.
   - Если общий сервер трогать нельзя, из терминала с ключом в корне репозитория
     запустите `opencode --standalone`. Этот клиент использует собственный сервер;
     проверяйте подключение через `/mcps` именно в нём. Обычный `opencode mcp list`
     обращается к общему серверу и не проверяет standalone-процесс.

   См. [фоновый сервер V2](https://opencode.ai/v2/docs/cli/#background-service)
   и [управление его жизненным циклом](https://opencode.ai/v2/docs/troubleshooting/#check-the-background-service).
3. При использовании общего сервера из корня репозитория выполните
   `opencode mcp list`: ожидается
   `render connected`. Без переменной подставляется пустая строка, аутентификация
   Render не сработает. Не публикуйте диагностический вывод с заголовками авторизации.
4. Перед запросами к ресурсам попросите агента перечислить workspaces и подтвердите
   нужный workspace. Передавайте его `workspaceId` в последующие запросы.
   Начните с чтения списка сервисов, без изменения инфраструктуры.

Не записывайте ключ в `opencode.json`, документацию или коммиты. OpenCode читает
переменную окружения процесса; `.env` автоматически этой настройкой не загружается.
Глобальную конфигурацию менять или копировать в репозиторий не требуется.
Проектная запись `render` заменяет одноимённую глобальную запись целиком;
остальные глобальные MCP-серверы сохраняются.

Локальный `vs-mcp` (`localhost:3001`, Visual Studio) намеренно не включён:
он зависит от окружения разработчика и не нужен для работы с Render.

## Подтверждение изменяющих операций

В V2 permission action для MCP имеет вид `<server>_<tool>`, в том числе в Code Mode.
Проект использует массив `permissions` с полями `action`, `resource`, `effect`:

| Action с `effect: ask`, `resource: *` | Что требует подтверждения |
|---|---|
| `render_create_*` | `create_web_service`, `create_static_site`, `create_cron_job`, `create_postgres`, `create_key_value` |
| `render_trigger_deploy` | Запуск deploy |
| `render_update_environment_variables` | Изменение переменных сервиса |
| `render_select_workspace` | Изменение выбранного workspace в состоянии MCP-сессии; предпочтительнее явный `workspaceId` |

Операции чтения (`get_*`, `list_*`, `query_render_postgres` с read-only транзакцией)
не получают новых правил: они сохраняют унаследованные permissions. Проект не
добавляет для них `allow`, чтобы не ослабить существующие ограничения пользователя.
Другие MCP-серверы эти правила не затрагивают. При обновлении каталога Render
проверяйте, не появились ли новые изменяющие инструменты вне указанных actions.

По [правилам V2](https://opencode.ai/v2/docs/permissions) применяется последнее
совпавшее правило. Глобальные permissions не удаляются, но совпадающее проектное
правило может переопределить их (в том числе заменить глобальный `deny` на `ask`).
Проектные правила дополняют настройки с меньшим приоритетом;
совпадающие правила из конфигурации с большим приоритетом и permissions конкретного
агента могут изменить результат. Поэтому проектный `ask` — не непереопределяемый
запрет. Сохранённое разрешение **Allow always** также может подавить запрос `ask`;
для разового согласования выбирайте **Allow once**. Организационные запреты
`policies` могут блокировать действие независимо от permissions.

Перед работой проверьте итоговые правила нужного агента, не вызывая изменяющие
инструменты. Например, из корня репозитория для агента `build` в PowerShell:

```powershell
$directory = [uri]::EscapeDataString((Get-Location).Path)
$agent = opencode api get "/api/agent/build?location%5Bdirectory%5D=$directory" | ConvertFrom-Json
$agent.data.permissions | Format-Table action, resource, effect
```

Это GET локального API общего сервера, не операция Render. Для другого агента
замените `build`; проверка общего сервера не описывает standalone-процесс.
Не публикуйте полный вывод `/api/config`: после подстановки он может содержать ключ.

**Важно:** не разрешайте изменяющие операции без отдельного подтверждения владельца.
Проверка подключения не требует redeploy; даже результаты чтения могут содержать
чувствительные данные, поэтому не публикуйте их без проверки.
